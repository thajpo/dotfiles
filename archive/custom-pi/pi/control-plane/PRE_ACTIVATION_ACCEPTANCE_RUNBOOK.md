# Pi Harness Pre-Activation Runbook

Owns: human pre-activation procedure.

The operator performs these steps from the controlling host TTY:

1. Identify the exact source tree, staged build, plan, catalog, schema, and
   evidence digests.
2. Confirm every dependency gate named by the root program has valid retained
   evidence for those identities.
3. Run the complete staged journey twice in independent disposable roots.
4. Confirm all conversational Pi/model/session/TUI processes were host
   processes and every writer tool action occurred only in its assigned
   controller-owned container.
5. Confirm the controller was the sole Docker and Git lifecycle actor, writer
   containers had no writable Git metadata or push path, and role authority
   came from the inherited authenticated controller channel.
6. Confirm Linux, npm package-lock, Python uv/hash-pin, unsupported-manager,
   separate TTY approval, restart, fault, installation, and rollback evidence.
7. Confirm historical Pi state/chats were untouched and unread, no remote
   provider or Git remote was contacted, no production mutation occurred, and
   OpenCode remains unchanged and usable.
8. Review all failures, STOP/SKIP results, planned catalog actions, stale
   evidence, and protected-surface deltas. Any occurrence blocks activation.
9. Review the exact cutover and rollback commands without executing them.
10. Either reject activation and preserve evidence, or explicitly approve one
    build ID and one cutover plan through the separate TTY-bound host CLI.

No model-visible tool, review verdict, test runner, environment variable, tmux
pane, or prior approval may perform or imply step 10.
